# FluentHub (fluent-toolkit)

WordPress plugin that unifies Fluent plugin admin UIs into one workspace, manages MCP for AI agents, and ships an updater + plugin installer dashboard.

## Build

- `npx mix` from plugin root rebuilds everything into `dist/`.
- No Composer autoload — `fluent-toolkit.php::loadClasses()` manually `require_once`s each class file. Add new classes there.

## Code map

- `fluent-toolkit.php` — bootstrap, AJAX handlers (`fluent_toolkit_save_dashboard_settings`, `fluent-beta-install`, `fluent_toolkit_activate_plugin`, MCP toggles), license/install logic.
- `Classes/AddonUpdatePusher.php` — injects the kit API's `overwrites` map (slug → version/url in `__fluent_toolkit_versions`) into the `update_plugins` transient at read time, so addon updates show on the Plugins screen before wp.org's ~24h update-check cool-down. Also refreshes that option piggybacked on WP's own update checks (throttled to 6h).
- `Classes/AdminMenu.php` — registers the `FluentHub` top-level menu + submenu links, enqueues the Vue dashboard.
- `Classes/UnifiedUiHandler.php` — wraps Fluent plugin admin pages with the unified sidebar template. Reads `_fluent_kit_settings` to decide whether to hide native admin menus / app headers.
- `Classes/UnifiedUi/MenuProviders.php` — one static class with `getCrmMenu()`, `getCartMenu()`, etc. Each returns `[item_key => {title, url, icon_svg, sub_menu?}]` or `[]` when the plugin isn't active.
- `Classes/UnifiedUi/Icons.php` — `Icons::get($key)` returns an inline SVG string by name.
- `src/unified-ui.js` → `dist/unified-ui.js` — sidebar DOM interactions (mobile drawer, WP menu drawer, theme toggle, hash routing, workspace switcher). Reads per-page flags from `data-*` attributes on `.fluent_uui`.
- `src/unified-ui.scss` + `src/unified-ui/_utilities.scss` → `dist/unified-ui.css` — sidebar styles.
- `src/components/Dashboard.vue` + `src/style.scss` — FluentHub admin dashboard (Vue 3 + Element Plus).
- `i18n.node.js` + `i18n.config.json` → `Classes/TransStrings.php` — generated Vue translation map (see Translations). `src/i18n.js` holds the `$t` / `$_n` / `$_x` runtime.
- `includes/Mcp/HubServer.php` — one MCP server for all Fluent plugins at `/wp-json/fluent-hub/mcp`. On `mcp_adapter_init` @1000 it reads each product's own server back from the adapter (product slug = server id) and lists two router tools per product, `{slug}-read` / `{slug}-write`, taking `{action, arguments}`. A call runs the product's own `McpTool` (`check_permission()`, the adapter's `mcp_adapter_pre_tool_call` / `mcp_adapter_tool_call_result` filters with the product's tool name and server, then `execute()`), so results match the product server. The `help` action is two-step so discovery stays cheap: without arguments it returns the product's server instructions and one line per action of that tool (read tool: read actions, write tool: write actions), with no schemas; `{"actions": [...]}` returns the instructions and the full definition of those actions, and `{"actions": ["all"]}` every action of the tool. The instructions hold the product's safety rules, so every form returns them. Output schemas are left out unless `{"output_schema": true}`. The router refuses input placed beside `action` (`misplaced_arguments`) and an `arguments` value that is not an object (`invalid_arguments`; a JSON object sent as a string is read), so an action never runs without the input the agent meant to send. Its own errors use the envelope and codes every Fluent MCP server shares (Fluent MCP standard v1): `{"error": {code, message, retryable, fields, ...}}` as the `WP_Error` message, with `invalid_param` for a wrong or missing value and `unknown_param` for a parameter that does not exist; the specific reason stays in the `WP_Error` code (`fluent_hub_wrong_tool`, ...). See `HubServer::ERROR_CODES`. `HubServer::sendResultOnce()` (on `rest_post_dispatch`, hooked by `armSingleResultCopy()` only after a hub tool ran, so other REST requests pay nothing) drops the adapter's `structuredContent` copy of a tool result on the hub route and keeps the text block: the adapter sends every result twice, and some clients give the model both copies (measured: Codex does, Claude Code gives only `structuredContent`). The router tools declare no output schema, so the text block alone is valid MCP. Filter `fluent_kit/mcp_hub_single_result_copy` turns it off. A product whose transport gate the user fails is hidden. Needs adapter 0.7.0+. Off by default: the "FluentHub MCP server" switch on the MCP page sets `_fluent_kit_settings['mcp_hub'] = 'yes'`, and the first time it also sets `mcp_oauth = 'yes'`, so one switch gives the endpoint and sign-in together. Products the admin leaves out (Advanced on the MCP page) are stored in `_fluent_kit_settings['mcp_hub_excluded']`. `HubServer::userCanConnect()` decides who may use the server at all, for sign-in and application passwords alike: users with a role in `_fluent_kit_settings['mcp_hub_roles']` (administrator is always in it), network admins, and whoever the `fluent_kit/mcp_hub_user_can_connect` filter lets in. The transport gate, the consent screen and the token endpoint all call it.
- `includes/Mcp/OAuth/` — OAuth 2.1 sign-in for the FluentHub MCP server only (`OAuthServer`, `AuthorizePage`, `Store`). All URLs live under `/wp-json/fluent-hub/oauth/` (resource metadata, `.well-known/openid-configuration` appended to the issuer, register, token, revoke) plus the consent screen at `wp-login.php?action=fluent_hub_authorize`, because the REST API ignores the login cookie without a nonce. The consent screen shows every error on the page and redirects to the client only after the user approves or cancels: registration is open, so an earlier redirect would be an open redirect. Nothing is served from the site-root `/.well-known/`. No custom tables: the signed `client_id` carries the client, a code is a 5-minute transient, and the access token is a standard application password whose `app_id` is `Store::APP_ID_PREFIX` plus the blog ID (`fhp_{user_id}_{password}`, no expiry, no refresh token; revoked on the user's profile or the MCP page; a new sign-in deletes the user's connections of the same app name that went unused for `Store::STALE_TOKEN_DAYS`, and keeps at most `Store::MAX_TOKENS_PER_APP`, the ones used longest ago go first). The blog ID matters on multisite, where users and their application passwords are shared by all sites: a token works, and is listed, only on the site that issued it. `OAuthServer::restrictPasswords()` keeps those passwords to Bearer on the hub route; core refuses them on Basic auth, other REST routes and XML-RPC. It is hooked in the plugin constructor, never inside `OAuthServer::register()`, because that waits for `AdapterBootstrap::boot()`, which a visitor can make fail with a query string (`action=activate&plugin=mcp-adapter/mcp-adapter.php`). The Bearer check runs on `rest_authentication_errors` @-1000, before plugins that refuse anonymous REST requests. Deactivating the plugin leaves them in place, and without the plugin nothing limits them to the MCP endpoint. No `client_secret_basic`: WordPress reads every Basic header as an application password login, so security plugins count each token request as a failed login. The routes do not depend on `wp_is_application_passwords_available()`, because security plugins turn it off per request. There are no scopes: a connection has the permissions of the user who approved it. Off by default and off whenever the hub is off (`HubServer::enabled()`); turning the hub on the first time sets `_fluent_kit_settings['mcp_oauth'] = 'yes'`, and the "Sign in with WordPress" switch under Advanced turns sign-in off alone.
- `includes/Mcp/AdapterBootstrap.php` — loads the bundled MCP adapter (`libs/mcp-adapter/`, an unmodified upstream release copy) on `plugins_loaded` @999, unless another plugin already supplies one. Reports the provider (`toolkit` / `plugin` / `other` / `missing`), version and source of the copy that actually runs, and flags an older copy that another plugin bundles so the FluentHub MCP page can show a note (no WP admin notice).

## Fluent MCP standard

`docs/mcp-standard.md` holds the rules every Fluent MCP server follows, the product servers and the hub alike: one error envelope, two input codes (`invalid_param`, `unknown_param`), `meta.warnings`, dates and money conventions, plain-English text for AI, each server working without the hub, one copy of each tool result, and no `outputSchema` by default. Read it before changing what an MCP server returns, and update it when a rule changes.

## Products and the hub connection

`docs/mcp-product-connect.md` is the contract for the "connect with one URL" card on each product's own MCP screen. A product reads `apply_filters('fluent_kit/mcp_hub_state', null, $slug)` (built by `HubServer::connectState()`, null when FluentHub is not active) and never calls our classes. The per-app sign-in instructions have one source, `OAuthServer::clients()`; the MCP page gets them in `oauth.clients`. A product admits its own non-admin managers to its own tools with the filter `fluent_kit/mcp_hub_product_user_can_connect`: `HubServer::productAllowed()` asks `userCanUseProduct()` per product, so such a user reaches that product only, and the consent screen and token endpoint ask `userCanConnectAny()`. A product screen turns the hub on for a user with `manage_options` through `apply_filters('fluent_kit/mcp_hub_enable', null, $slug)` (`HubServer::enableFromProduct()`): it only turns on, never off, and it leaves sign-in as the admin set it.

## Settings

- Stored in `_fluent_kit_settings` option (array).
- Whitelisted keys (set via `saveDashboardSettings()` AJAX): `uinified_ui` (typo intentional — don't fix, would break existing installs), `merge_admin_menus`, `hide_app_headers`.
- Defaults on first Unified UI activation: `merge_admin_menus = yes`. Existing users who already had it on don't get the key set, so they keep their menus visible until they opt in.
- `hide_app_headers` is opt-in for everyone (default off).

## Gotcha: other Fluent plugins strip foreign scripts

FluentCRM and friends call `wp_dequeue_script()` on non-Fluent scripts on their own admin pages. `wp_enqueue_script()` from this plugin gets removed silently. Print `<script src>` directly via `admin_print_footer_scripts` instead (see `UnifiedUiHandler::printUnifiedUiScript()`). CSS via `wp_enqueue_style()` is not stripped — that path is fine.

## Gotcha: the MCP adapter registers its abilities too late

Core's Abilities API registry is a lazy singleton — `wp_abilities_api_init` fires once, on the first `WP_Abilities_Registry::get_instance()` call, and never again that request. `McpAdapter` only adds its `wp_abilities_api_init` / `wp_abilities_api_categories_init` listeners from `McpAdapter::init()`, which runs on `rest_api_init` @15, so any other plugin registering an ability on `init` fires the hook first and the adapter's three abilities (`mcp-adapter/discover-abilities`, `get-ability-info`, `execute-ability`) never register. The default server then logs "ability does not exist" for each one on every REST request.

`AdapterBootstrap::hookDefaultAbilities()` adds those same listeners at `plugins_loaded`, before the registry can be built. It reuses the adapter's own callables so WordPress dedupes when `McpAdapter::init()` adds them again — don't wrap them in closures, that double-registers the abilities. Don't "fix" this by hooking `McpAdapter::init()` to `init` early either: that also pulls forward `DefaultServerFactory::create()`, which fires `wp_abilities_api_init` at `init` @1 and breaks every other plugin that registers abilities at `init` @10.

Fixed upstream in adapter 0.7.0 (`McpAdapter::instance()` now adds the listeners). Keep the workaround: another plugin can still load an older copy in place of ours.

## Gotcha: other plugins bundle the MCP adapter without its constants

Rank Math (1.0.280 ships 0.5.0) loads the adapter as a plain Composer library from its main file: it prepends its autoloader and calls `McpAdapter::instance()`, but defines neither `WP_MCP_VERSION` nor `WP_MCP_DIR`. PHP cannot replace a class that is already loaded, so requiring our copy then only puts our constants over their classes. `AdapterBootstrap::adoptAdapterLoadedElsewhere()` checks for `\WP\MCP\Core\McpAdapter` before loading ours, and defines `WP_MCP_VERSION` from the loaded class's `VERSION`, because the Fluent plugins check that constant before they register their servers. Read the running version and location from the class (`McpAdapter::VERSION`, reflection), never from `WP_MCP_VERSION` / `WP_MCP_DIR`. Only copies that other plugins bundle get the outdated note on the MCP page. The official standalone MCP Adapter plugin never does, because it updates through wp.org.

## Conventions

- PHP namespace: `FluentToolkit\Classes` (handler) / `FluentToolkit\Classes\UnifiedUi` (helpers).
- Vue dashboard talks to the backend via `this.$post(action, data)` / `this.$get(...)` (mixin defined in `src/app.js`). All actions require the `fluent_toolkit_nonce`.
- Sidebar root div carries class chains: `fluent_uui [fui-hide-app-headers|fui-has-app-headers] fui_app_{slug}` and `data-has-dark-mode="0|1"`. JS reads dark-mode flag from that attribute.
- The mobile breakpoint is `782px` (matches WP admin).
- Icon colors in the dashboard settings list: indigo / violet / amber — see `.ft-setting-icon--*` in `src/style.scss`.

## Translations

Use translations consistently: `__('text', 'fluent-toolkit')` in PHP and `$t('text')` in Vue. Do not split a sentence across several `$t()` calls or concatenate a `$t()` result with a value; use placeholders (`$t('Update to %s', version)`, `$_n('%s update', '%s updates', n)`) and `$_x('Ready', 'MCP status')` when one English word needs different translations in different places. Vue strings reach translators through the generated `Classes/TransStrings.php`, localized as `fluentToolkitVars.i18n`: after adding or changing `$t()` / `$_n()` / `$_x()` strings run `pnpm run translate` and commit the regenerated map (`build.sh` regenerates it before linting, so the zip is always current, but a stale committed map drifts from what ships). Put a `<!-- translators: ... -->` or `// translators: ...` comment on the line directly above any string with placeholders (and `/* translators: ... */` above PHP `sprintf(__())`); the lint fails on a placeholder string without one, on em/en dashes in UI text, and on keys with leading or trailing whitespace. Paragraphs of 120+ characters go in `src/reservedWords.json` under a short `Snake_Case_Key` and the template calls `$t('Snake_Case_Key')`. See `docs/js-translations.md`.

## Dashboard plugin icon

`AdminMenu::pluginIcon()` returns a base64 SVG data URL. WP masks menu icons to a single color, so the icon must be a monochrome silhouette (rounded square with the "F" marks cut out via `fill-rule="evenodd"`). Don't use a multi-color logo here — it'll flatten.
